# Conventions catalog

Detailed maintenance conventions preserved from the former root agent guide. The concise rules are
in [`AGENTS.md`](../../AGENTS.md), with readable explanations in
[`conventions.md`](../conventions.md).

- **Performance is a top priority.** Editora must stay fast and responsive, especially on large files. Treat the UI thread as sacred and these as the hot paths: typing/editing, scrolling, syntax highlighting, the document overlays (whitespace, minimap, 80-column ruler), and the line-number gutter. Rules to uphold:
  - **Never block the JavaFX Application Thread** with non-trivial work — tokenize/parse/search off-thread (see the `highlightExecutor` pattern in `EditorBuffer`) and apply results back on the FX thread with a generation/stale-result guard.
  - **Debounce and coalesce** — re-highlighting is debounced; overlay/ruler/minimap redraws coalesce to one per pulse (a `pending` flag + `Platform.runLater`). Don't add per-keystroke or per-scroll-pulse work that isn't coalesced.
  - **Work incrementally / only on what's visible** — highlighting re-tokenizes only from the changed line; overlays iterate just the visible paragraphs (`firstVisibleParToAllParIndex … last`) and skip folded lines. Avoid O(document) work on edits or scrolls.
  - **A settings apply must not redo unchanged work — every view setter guards on its own value.** `applyViewSettingsToAllBuffers` pushes ~40 settings into *every open buffer* and re-runs ~25 `applySupport()` calls, and it is the path behind **every** toggle (Simple mode, tool stripe, line numbers, a theme change, a Settings checkbox). So a setter that does real work when handed the value it already holds pays that cost N buffers × every toggle. Measured on the Simple-mode toggle with five source files open (FX harness + a 2 ms sampler attributing each sample to its deepest `com.editora` frame): **230–550 ms → 48–108 ms** (median 233 → 55). The four culprits, each now a one-line guard, and each a *shape* to watch for rather than a one-off: **(a)** `FoldManager.shadeHeader` cleared the fold shade on *every region in the file* with an unconditional `area.setParagraphStyle(...)` — a **styled-document mutation, not a property write** (442 of 758 samples; thousands of rebuilt paragraphs in a large source file, almost none of which were ever shaded); **(b)** `EditorBuffer.columnRulerX` re-measured the ruler — **two** forced `VirtualFlow` layouts (`firstVisibleParToAllParIndex` + `lastVisibleParToAllParIndex`) plus character-bounds queries — for every open buffer **including background tabs**, so `setFont`/`setColumnRulerVisible` now no-op when unchanged and `scheduleRulerMeasure` skips a buffer that isn't the visible tab (`setRenderingActive` re-schedules it when the tab returns, so nothing is left stale). **The bigger half was the trigger, not the callers:** it was subscribed to `area.viewportDirtyEvents()`, which fires for a **vertical scroll and for every edit** — neither of which can move the ruler, whose x is only (glyph advance, gutter width, horizontal scroll), with the viewport width deciding the show/hide. Measured at **6–7 full measures per chrome toggle** and one per keystroke. The subscription now schedules only on a viewport **width** change; horizontal scroll keeps its own `estimatedScrollXProperty` listener; and everything else that moves the ruler marks it explicitly via **`markRulerInputsDirty()`** (`refreshGutter` — the gutter's width is where column 0 starts — plus `setFont`, `setWordWrap`, `setColumnRulerVisible`, `setRulerColumn`). **The flag is cleared only by a measure that actually produced a position**: before the area's first layout the geometry is unmeasurable and `columnRulerX` returns null, and clearing it there would leave the gate waiting on a width change that may never come, hiding the ruler for the life of the buffer. `setRulerColumn` also stopped measuring **synchronously** on every `applyEditorConfig` (i.e. every buffer, every settings apply); 6–7 measures per toggle → 1–2; **(c)** `refreshGutter()` — which rebuilds every visible row's graphic — ran **twice per buffer per apply** because neither `setGutterVisible` nor `setLineNumbersVisible` compared its argument; **(d)** `applyEditorTheme` removed and re-added the *same* stylesheet, forcing a full scene CSS reapply. **Two traps when adding such a guard:** the field's declared default is only an *assumption* about the widget (hence `setFont`'s `fontApplied` flag — the area's inline style and the overlays' fonts are set by that very call, so the first one must always apply), and a setter that callers deliberately re-invoke to *re-derive* an effective value (`setMinimapVisible(minimapVisible)` after a large-file/preview-mode change) must guard on the **effective** result or not at all. **`ColumnRulerFxTest` keeps the ruler honest on both halves** — that a pure gutter-width change (toggling line numbers, *not* Simple mode, whose minimap hide also resizes the area and would therefore pass through the width trigger even with the mark removed) still moves it, and that an edit re-measures it **zero** times; both were mutation-checked, and a third assertion that a toggle costs "at most N" measures was **dropped for passing either way** in a one-file fixture. `EditorBuffer.RULER_MEASURES_FOR_TEST` exists for that second half: the position alone cannot show a regression to measuring far too often.
  - **Don't defeat the per-node CSS style cache** — keep token rules as the compound `.text.<class>` selector (see `syntax.css`); coalesce adjacent same-style spans (`SpanMerger`) before `setStyleSpans`; never query `getCharacterBoundsOnScreen` synchronously inside a layout/viewport event.
  - **Never call the zero-width `getCharacterBoundsOnScreen(x, x)`** — always measure a one-character range. For an *empty* range `GenericStyledArea` allocates a throwaway `CaretNode` to measure with, and a `CaretNode` starts a 500 ms `restartableTicks` blink timer that **nothing ever stops**, so each call permanently registers a running `Timeline` as a JavaFX pulse receiver. `EditorBuffer.caretBounds` (the 80-column ruler) did this 2–3× per measurement and re-measured on `viewportDirtyEvents`, i.e. **every edit**: measured **+2 leaked timers per keystroke**, with typing latency degrading **5.6 ms → 28 ms over 2000 keystrokes** and never recovering — the leak outlives the window that caused it. Confirmed on both the headless/software and the real GTK/es2 pipeline, so it is not a test artifact. Fixed by measuring `(abs, abs+1)`, and at end-of-paragraph the last character's right edge (same x, no allocation): receivers went `+2.02` → `+0.03` per keystroke and latency to a **flat ~2 ms**. There are ~30 `getCharacterBoundsOnScreen` call sites (every overlay); the non-empty-range ones take a different path and are fine. **When adding one, never pass an empty range** — measure a one-character range, as `caretBounds` (root-local, overlays) and **`caretAnchorBounds`** (screen, caret-following popups) both do. The completion popup, its LSP variant and the quick-fix list all measured the leaking way and leaked **exactly one timer per open** (mutation-measured) until they were routed through `caretAnchorBounds`; `TypingLatencyBenchmarkTest.openingACaretAnchoredPopupDoesNotLeakPulseReceivers` guards that. **Anchoring a popup needs `caretAnchorBounds`' fallback chain**, and that is the part that bites: the leaking form measured through a caret it had just created, so it answered even when nothing was rendered, whereas a *character* is only measurable once its paragraph is laid out — empty whenever the flow has no cell for that line. Returning null there makes the popup **silently not open**, so the chain is character → `getCaretBounds()` → the area's own top-left. `CodeArea.getCaretBounds()` is second and is **not a substitute** for measuring (it reports the *rendered* caret, empty whenever the area isn't focused). Both failure modes are **order-dependent** — `CodeActionPopupFxTest` passes alone and fails only in the full suite — so verify a change here with a full `./mvnw test` — the cost is invisible until the editor has been typed in for a few minutes. Guarded by `TypingLatencyBenchmark` (`@Tag("fx")`), which counts pulse receivers per keystroke.
  - **Large/huge files** already disable highlighting + minimap (≥5 MB) and go read-only with a capped load (≥50 MB); preserve those guards. There's also an **intermediate large-source tier** (`EditorBuffer.heavyFile` / `setHeavyFile` / `isHeavyFile`, set in `MainController.loadInto` when a sub-5 MB file's `lineCount()` ≥ `Settings.largeFileThreshold`, default 10000 lines, 0 = off): it **disables the minimap + LSP** (the two heaviest features for a very long single source) but **keeps syntax highlighting + editing**; `largeFile` implies the same minimap/LSP suppression. Per-buffer toggleable (`view.toggleLargeFileMode` → `MainController.toggleLargeFileMode`, which flips `setHeavyFile` then `syncBufferLsp`); threshold via `editor.setLargeFileThreshold` + Settings → Editor → Performance. Bound memory (undo history is capped; loads are capped). **Undo granularity:** `boundedUndoManager` builds the RichTextFX manager with `UndoMerge.PAUSE` as the `preventMergeDelay` (idle break) and a `plainTextChanges` subscriber calls `UndoManager.preventMerge()` at word/whitespace/newline boundaries (pure `editor/UndoMerge.breakAfter`), so one `C-z` undoes a word/line instead of the whole contiguous burst RichTextFX would otherwise merge; split views share the document so both managers are broken together. **Undo History tool window** (`ui/UndoHistoryPanel`, id `undoHistory`, `Side.RIGHT`, `tool.undoHistory`/`M-g u`, buffer-gated; **registered default-hidden** via `register(tw, false)` — the stripe button is off until the user enables it via Settings → Tool Windows or `tool.undoHistory`, since the `undoHistory.jump` popup is the primary entry point): `editor/UndoHistory` keeps a capped (50) in-session list of full-document checkpoints captured on the `UndoMerge.PAUSE` debounce (`EditorBuffer.captureUndoCheckpoint`, skipped for huge/>1 MB files); the panel lists them newest-first (time + caret-line preview) and double-click/Enter calls `EditorBuffer.restoreUndoCheckpoint` (an undoable `replaceText`). A **popup alternative** — command `undoHistory.jump` (`M-g v`; `MainController.undoHistoryPalette`, a `QuickOpen<UndoHistory.Checkpoint>` over the active buffer's `entriesNewestFirst()`, seeding a baseline when empty like the panel) — opens the same checkpoints as a filterable in-scene overlay (label = caret-line preview, detail = `HH:mm:ss`); Enter restores. Session-only, finer-grained than save-based Local History; pure bits (`UndoHistory.add`/`lineAt`/`clamp`) unit-tested.
  - **Bound retained GPU textures.** JavaFX's Prism texture pool has a fixed ceiling (default 512 MB); exhausting it makes the render thread NPE (null `RTTexture`/mask texture) → a black window — seen only in the packaged build. So don't let GPU-backed resources grow with the number of open files: a background (non-selected) tab's buffer drops its minimap snapshot via `EditorBuffer.setRenderingActive(false)` (driven from the tab-selection + tabs-added listeners; `Minimap.setRenderingActive` nulls the cached snapshot and stops rendering, regenerating on show), and the `PreviewImageLoader`/`MermaidImages` image caches are **LRU-bounded** (not unbounded `ConcurrentHashMap`s) since each holds an `Image` (a pinned texture). The `dist` jpackage app (and `mvn javafx:run`) also raise the caps as a safety net (`-Dprism.maxvram=2G -Dprism.maxTextureSize=16384`). When adding any per-buffer Canvas/Image, make sure it's released or bounded.
  - **Packaged-runtime JVM tuning (footprint + install size).** The `dist` jpackage `<javaOptions>` (mirrored into the `javafx:run` options so dev == prod) cap the heap and GC: **`-Xmx2g`** (without it, jpackage inherits the default ergonomic max heap ≈ ¼ of physical RAM — multi-GB on a high-RAM box — which lets GC-driven RSS balloon; 2g is predictable across the release matrix and safe for a 50 MB huge-file load + capped undo), **`-Xms64m`** (set **explicitly**, because the ergonomic initial heap is 1/64 of physical RAM **clamped up to `-Xmx`** — on a 128 GB box that *equals* `-Xmx`, so the **whole 2 GB heap is committed before `main` runs**. Measured, Linux, installed `.deb`, 4-file session: peak RSS median **908 MB** (888/888/929/927, n=4) held for **~58 s** until the periodic GC uncommits, vs **653 MB** (n=6) with `-Xms64m` — ranges do not overlap. **Startup is unaffected** (5 interleaved pairs, mean −27 ms) and **pauses get better, not worse**: a small young gen collects far less, so STW pauses went **19.6 → 4.2 ms median, 31.7 → 9.0 ms max**. The live heap is only **63–75 MB** idle, so 64m costs nothing to grow from. It scales with the *host's* RAM, so a 16 GB laptop never sees it — the same 'predictable across the matrix' argument that pins `-Xmx`. `scripts/aot_build.java` **must mirror it** or the cache is trained under a heap layout that depends on which machine built the release; `AotTrainerOptionsTest` fails the build if it drifts) and **`-XX:+UseG1GC -XX:G1PeriodicGCInterval=30000`**. **GC thread counts are deliberately NOT pinned**: ergonomics sizes them from the core count, so a 24-core box gets 18 parallel / 18 refinement / 5 concurrent threads for a ~65 MB live set and G1's structures cost ~1.5 MB per thread (NMT `GC` committed **76 MB**, falling to **56 MB** at 8/2/8 with pauses unchanged) — but a fixed value is a **floor as well as a ceiling**, so `-XX:ParallelGCThreads=8` would *raise* it from 4 to 8 on a 4-core laptop and cost memory on exactly the machines that can least afford it, and the flag has no cap-only form. This **was `-XX:+UseSerialGC`** on the reasoning that a mostly-idle single-user editor gets sub-ms pauses from it with no parallel GC-thread overhead, and lower idle RSS than G1 — **every part of which measurement contradicted** (Linux, packaged app image). SerialGC's `NewRatio` under `-Xmx2g` sizes **eden at ~548 MB** and it **never uncommits**, so hundreds of MB of garbage sit resident against a **~72 MB live set** (forced-full-GC figure) — and a young collection has that much to copy, so pauses are **not sub-ms**. Measured on a **real session** (one Markdown file in SPLIT preview + the project tree, maximized), SerialGC → G1: **RSS 1167 → 733 MB (−37%)**, **max pause 186 → 35 ms** (median 133 → 8 ms), **startup unchanged** (−42 ms over 8 interleaved pairs, inside the noise floor). A 186 ms pause is eleven dropped frames, on the typing path this file treats as sacred. The synthetic single-small-file case understates it (647 → 471 MB, 66 → 22 ms) — **measure on a real session, the allocation rate is what drives this**. `G1PeriodicGCInterval` is load-bearing: it's what returns idle memory to the OS; plain G1 keeps the committed heap much like SerialGC (1013 MB). **30 s, not 5 s** — a 5 s interval settles at a *higher* RSS (780 MB) and costs **1.00% idle CPU vs 0.40%**, so the extra wakeups buy nothing and keep the CPU out of deep idle (battery); the only cost of 30 s is up to ~30 s before memory is released after a burst. Idle CPU vs SerialGC is +0.15pp (0.25 → 0.40%) — the price of the 434 MB. Cheaper half-measures were tried and are strictly worse: `-Xmn64m` −146 MB but +33 ms startup, `-Xmx512m` only −37 MB (the **young gen**, not the ceiling, is what's resident). If large-file GC *hitching* ever shows up, generational ZGC is the smoothness-over-footprint alternative. **Two traps when measuring memory, both of which produced wrong conclusions here.** (a) **`jcmd GC.run` + `GC.heap_info` does not give you the live set** — `ExplicitGCInvokesConcurrent` is false so `System.gc()` is a full GC, but `used` read a few seconds later can still be **2× the live bytes** (measured 216 MB vs 103 MB live) because the collection has not settled; reading it that way invented a phantom '+162 MB per 50 edits' accumulator that does not exist (with the undo checkpoints disabled, 50 edits cost **−4 MB**). Use **`GC.class_histogram`'s total**, which forces its own STW full GC and reports live bytes. (b) **Settled RSS has a ±90 MB run-to-run noise floor** (two runs of an *identical* config landed at 552 and 688 MB — the variance is how much of the heap region stays resident after an uncommit), so judge a change on **peak RSS and NMT category totals**, which are stable to the megabyte, never on one settled reading. Also: a `Concurrent Mark Cycle` line in the GC log is **not a pause** — grep `GC(n) Pause ` or you will report concurrent work as latency. **Re-measure before changing this**: `-Xlog:gc:file=…` for pauses, `VmRSS` sampled at 30 s *and* ~120 s (a 30 s interval hasn't fired yet at 30 s — reading RSS too early makes G1 look worse than SerialGC), **repeated** samples for idle CPU (single 20 s samples swing 0.2–3%), and **interleaved** A/B for startup — sequential runs 20 minutes apart drift enough to invent a 12% regression that paired runs show doesn't exist. The jpackage `<jLinkOptions>` strip the bundled runtime (`--strip-debug --no-man-pages --no-header-files --compress=zip-6`) → smaller DMG/MSI/DEB + less mapped footprint. (`--strip-native-commands` is deliberately *omitted* from jLinkOptions — `bin/java` must survive the jlink step for the AOT training run below; the `aot_build` helper deletes `bin/` itself afterward, reclaiming the same footprint. The runtime's `bin/` is never used at launch — the jpackage native launcher starts the JVM via `libjli`, and every external tool (java/python/node/git/LSP/DAP) is resolved via the augmented PATH. **WINDOWS EXCEPTION (`aot_build.java` strips `bin/` non-Windows-only):** the Windows JDK layout puts the JVM *inside* `bin/` (`runtime\bin\server\jvm.dll` + the bootstrap `jli.dll`/`java.dll`/`jvm.cfg`/…), and `Editora.exe` loads `jvm.dll` from there — so deleting `bin/` on Windows makes the launcher die with *"Failed to find JVM in …\runtime directory"* (a shipped regression fixed by guarding the strip to non-Windows). On Windows the whole `bin/` is kept — its launcher exes are a negligible footprint.) **AOT cache (JDK 25 Leyden) — implemented, ~28%/≈300–480 ms faster cold start** (measured macOS: first-frame ~1060 ms → ~760 ms; delivered-app wall delta ~480 ms): the build does a **two-phase jpackage** — phase 1 (`prepare`) jlinks an `APP_IMAGE` into `target/aot-image` with `-XX:AOTCache=$APPDIR/editora.aot` baked into the launcher `.cfg`; then `scripts/aot_build.java` (run by `exec-maven-plugin` with the build JDK) **trains a full-GUI cache against the image's own runtime** (so archived classes match the shipped runtime, path-independently — it maps after the install-dir move because the classes live in the jlinked `lib/modules`, keyed to the runtime image not absolute paths), writes `editora.aot` into `$APPDIR`, strips `bin/`, then either copies the image (APP_IMAGE builds) or wraps it into the installer via `jpackage --app-image` (DMG/MSI/DEB). **A *headless* trainer gives ≈0 win** — the gain is JavaFX scene/control/CSS class loading, which only loads when a window renders; the training run is the real GUI driven by `-Deditora.aotTrainExit` (`WindowManager` renders the first frame, settles ~2.5 s for highlight-class coverage, then `System.exit`). On Linux the helper auto-wraps training in `xvfb-run` (release.yml installs `xvfb`+GTK/GL libs on the Linux legs); macOS/Windows runners use their session. **The trainer pins `-Dprism.order=es2,sw` (#399)** — the one launcher option it deliberately does *not* mirror. Training must not depend on the host having a **real GPU**: CI runners present virtualized ones, and once JavaFX 26 made **Metal** the macOS default, the macOS **arm64** runner's paravirtual GPU aborted the trainer outright — `-[AppleParavirtDevice newArgumentEncoderWithLayout:]: unrecognized selector`, an Obj-C `NSException`, i.e. an `abort()` that Prism's own `mtl→es2→sw` fallback chain cannot catch (a *pipeline* fallback can't rescue a process-level abort). **That shipped macOS arm64 uncached from v0.9.1 through v0.9.8** — every tagged release — while x64 (a different virtual GPU) trained fine every time; it never reproduced on real Apple silicon, which has a proper Metal device, which is exactly why device-testing missed it. *(Both premises in the original bug report were wrong: it was never "both macOS legs", and never a v0.9.4 regression — check the per-leg `[aot]` lines in the release logs before believing a summary.)* The trade: the cache then archives es2's pipeline classes rather than Metal's, but the bulk of the win (scene graph, controls, CSS, editor, highlighting) is pipeline-independent, an archived class the runtime doesn't use is dead weight rather than a correctness problem, and anything not archived just loads normally. *(The "a headless trainer gives ≈0 win" note above predates JavaFX 26's built-in Headless Glass platform, under which a scene genuinely renders into a buffer — worth re-measuring as a more portable trainer that would also drop the `xvfb-run` dependency.)* **Failure-tolerant, but no longer silent:** the build still continues and ships uncached (a missing/invalid `-XX:AOTCache` logs to stderr and starts normally under `AOTMode=auto`), but `aot_build.java` now reports the trainer's **exit code** (previously discarded, so a crashing trainer was indistinguishable from a clean run and the only symptom was the absent file), writes a per-target row into `$GITHUB_STEP_SUMMARY`, and raises a GitHub **`::error` annotation** naming the target (`EDITORA_TARGET`, set from the release matrix) — a missing cache is a silent ~28% cold-start regression that nothing downstream notices. **`EDITORA_REQUIRE_AOT=1`** upgrades that to a hard build failure, and **release.yml now wires it at `'1'`** — armed once v0.12.1 trained on all five targets (72-73 MB each), the green tag it had been waiting for. When it fires, `reportNoCache` exits 3 → exec-maven-plugin fails the build → that matrix leg fails → the `Release` job (which `needs` the matrix) never runs, so **nothing publishes** rather than one platform shipping quietly slow. The whole chain was verified before arming — including that exit 3 actually fails Maven, since a gate that doesn't is worse than none. Note the gate covers the two paths that mean "we tried and got no cache" (training produced no file — the macOS arm64 case — and java/cfg not locatable); a **missing image dir** still just skips, because jpackage would already have failed. If it ever fires on a legitimate release, set it back to `'0'` for that tag and fix the trainer — don't weaken `aot_build.java`, whose job is to notice. It stays unset (non-fatal) for local and dry-run builds. **ADAPTER CACHING IS OFF (`-XX:+UnlockDiagnosticVMOptions -XX:-AOTAdapterCaching`, on the launcher AND the trainer) — do not remove.** The cache archives generated machine code, not only class metadata (`[aot,codecache,init] Loaded 974 AOT code entries`), and the i2c/c2i **adapters** in it are compiled for the CPU that *trained* the cache. GitHub's Linux runners are AVX-512 Xeons, so **v0.13.0 shipped adapters whose register-spill sequence starts in VEX/AVX (`c5 fb 11 …`, xmm0-15) and continues in EVEX/AVX-512 (`62 e1 ff 08 11 …`, xmm16-31)** — and the JVM **maps such an archive without complaint** (its CPU-feature validation does not cover cached adapters), so the first thread to reach one dies `SIGILL`/`ILL_ILLOPN`. Measured on a 13th-gen Core i7 (Raptor Lake, AVX-512 fused off): **4/6 launches aborted**, on a different thread each time (spell-dictionary-builder, editor-highlighter, the FX thread) — which is why it reads as flaky rather than as a hard failure, and why `--version` never reproduces it (it exits before the GUI). **This is a lottery on the builder's CPU, not on our code**, so it can silently affect any release and **CI cannot catch it** — the instructions are legal where they were generated. Diagnosis: the `Instructions:` dump in `hs_err_pid*.log`, where a `62`-prefixed opcode at the faulting `pc` is EVEX; `-XX:AOTMode=off` vs `-XX:-AOTAdapterCaching` over ~6 runs separates 'the cache' from 'the adapters'. **The adapters buy nothing** — first paint 1024 ms with them off vs 1704 ms with the whole cache off — so dropping them keeps the entire win; the trainer passes the flags too, so a new cache has no adapter code at all, while the launcher flag protects a user still holding a poisoned one. `AotTrainerOptionsTest` fails the build if either flag is dropped from either side. **Cost: the cache is ~72 MB** (measured across all five targets at v0.13.0: 72-73 MB), so the installed image grows accordingly (the DMG/MSI/DEB compress it — the v0.13.0 DMG downloads are ~106-108 MB). **Prism pipeline order is per-OS** (the `${prism.pipeline}` property set in the `os-mac`/`os-windows`/`os-linux` profiles, passed as `-Dprism.order=${prism.pipeline}` to both the dist `<javaOptions>` and `javafx:run` `<options>`): **macOS = `mtl,es2,sw`** — the **Metal** pipeline, added in **JavaFX 26**, which fixes the blank/garbled render-to-texture glitches the deprecated es2/OpenGL backend produced on Apple silicon (e.g. M-series: empty breadcrumb crumbs + tool-stripe icons); es2/sw stay as fallbacks since Metal is opt-in. **Windows = `d3d,es2,sw`** (must keep Direct3D — a blanket `mtl,es2,sw` would strip d3d and lose Windows GPU accel). **Linux = `es2,sw`**. JavaFX 26 runs on JDK 24+, so the JDK stays **25**. Still a **commented-out opt-in** in the pom (DEVICE-TEST before enabling, touches correctness): JDK 25 **compact object headers** (`-XX:+UseCompactObjectHeaders`, experimental, ~10–20% live-heap cut — note it changes the AOT cache's recorded layout, so retrain after enabling). *(Aside: `App.main` exits `--version`/`--help` via `System.exit(0)`, not a bare return — launching this `Application` subclass in module mode pre-starts the FX toolkit, whose non-daemon keep-alive thread would otherwise hang the process after `main` returns.)*
  - **Assess and report the performance cost of every change.** For any implementation or bug fix, evaluate its cost on the hot paths (allocation per keystroke/scroll, added FX-thread work, extra layout/CSS passes, memory) and tell the user about it — even if it's "negligible." If a change risks a regression, measure rather than guess — **for startup there is a permanent harness: `perf/Startup` + `scripts/measure-startup.sh`** (below).
  - **Startup timing — `com.editora.perf.Startup`.** Phase marks from launch to the **first rendered frame carrying the file's content** (`main` → `fx-start` → `config-loaded` → `fxml-loaded` → `controller-init` → `window-built` → `window-shown` → `file-loaded` → `first-paint`). **Off unless `EDITORA_PERF=1` / `-Deditora.perf`**, and when off every `mark()` is one static boolean test, so it ships inert; `EDITORA_PERF_EXIT=1` halts at first paint for a repeatable loop. Run it with **`scripts/measure-startup.sh -n 5 -c <configDir> <launcher> [args…] <file>`**, which reports the **median** (run 1 is always cold — page cache, GPU init — so a mean lies). **Two traps this harness exists to avoid, both of which produced confident nonsense first time:** (a) the timing **origin** — `ProcessHandle.startInstant()` is derived from boot time on Linux and drifted ~500 ms *early*, reporting a first paint **later than the process had existed**; the script now stamps `EDITORA_PERF_T0` (epoch millis) immediately before exec and `Startup` prefers it, labelling the output APPROXIMATE when it falls back. **Always sanity-check a reported number against externally measured wall-clock** — reported must be *below* wall. (b) `first-paint` is marked on the **second** `AnimationTimer` tick after the content load, because a tick fires at the *start* of a pulse: the second one proves the pulse that laid out and painted the content completed (≈1 frame of resolution). The mark is taken on the **first** loaded buffer and deliberately **not** gated on `buffer == activeBuffer()` — on the fresh-open path `loadInto` runs *before* the tab is added, so that guard silently never fired and the run never reported at all. **Measured baseline (Linux, packaged `.deb`, `--expert --single-window --no-session`, a 185-line file): ≈1.37 s to first paint** — 28% pre-`main` (launcher + JVM boot), 8% config, 16% FXML + `controller.init`, and **39% in the final load→paint segment** (FX layout/CSS/text render; the window is on screen ~570 ms before it shows content). **A/B results worth not re-deriving: the AOT cache is worth ~830 ms (38%) — 1.38 s with vs 2.22 s without, and almost all of that saving is class loading *after* `main`, so the 70 MB mapping is nearly free; the typst preview costs only ~70 ms and LSP startup only ~37 ms** (already off the critical path via the `lsp-start` pool) — so neither is the place to optimise, despite both being the intuitive suspects. **`EDITORA_PERF_SAMPLE=1`** (on top of `EDITORA_PERF`) adds an **FX-thread stack sampler** (`Startup.startSampler`, armed in `App.start`, 5 ms, daemon): each sample is blamed on its **deepest `com.editora` frame** — a JDK/JavaFX leaf says what is running but not which app code asked for it — and **tagged with the phase in progress**, so a gap is attributed rather than smeared over the whole startup. It exists because the last stretch before `first-paint` is bounded by two animation-timer ticks (~33 ms of real frames), so anything longer means the FX thread was *busy* and pulses weren't running at all — "rendering is slow" is the wrong reading, and the call graph named the wrong culprit twice. (Read the phase *before* taking the samples lock: `report()` holds `MARKS` then formats samples, so the other order inverts the lock order.) **The three costs it found, all fixed, worth ~180 ms combined** (interleaved A/B, packaged Linux, `--expert` + a 1-file session: median 1683 → 1503 ms; the `--no-session` desktop-launch form 1468 → 1397 ms, where only the first two apply): **(a) the minimap** — the single largest piece of app code before first paint (~135–230 ms), because `renderContent` walks every paragraph then calls `canvas.snapshot()` (a synchronous full-scene layout) and ends in `drawViewport`'s `firstVisibleParToAllParIndex()` (a forced `VirtualFlow` layout), and the startup triggers arrive as a burst (colors, tab size, content settle) so it ran **three times over** before the text appeared; renders now coalesce to one per pulse and the **first is held two animation frames** so the editor paints first (`Minimap.renderContent`/`renderNow`). **(b) `DapManager.configure`** re-resolved the python/js adapter locations on the FX thread (~30–50 ms of directory walking) for values not read until a debug session launches — and `detectPython`/`detectJs` relocate the same paths off-thread moments later anyway, so the synchronous half was pure duplication; the **java** bundle's `locate()` stays synchronous (documented race: it must reach the LSP layer before jdtls starts). **(c) `fillSessionFiles`** filled the *background* session tabs in the very pulses laying out the front-loaded one, so it now yields two frames after `k == 0` (`MainController.afterNextPaint`; `SessionRestoreDeferralFxTest` pins that the deferred files are still all restored — an `AnimationTimer` bug there would strand every background tab empty, far worse than the ms it saves). **(d) `FoldManager.recompute` queried the viewport unconditionally** — `firstVisibleParToAllParIndex`/`lastVisibleParToAllParIndex` force a `VirtualFlow` layout (the trap documented above), and it paid one to find a viewport for a `changed` set that was **empty**, i.e. a loop that does nothing; the query is now guarded on `!changed.isEmpty()`. This is as much a **typing** fix as a startup one (recompute runs on every 250 ms edit settle and most edits don't move a fold boundary), and it also stops the query's `estimatedScrollY` side effect firing on no-op runs. **Measured per-recompute at startup** (probe, `--expert` + a pom.xml session tab): the setLanguage-triggered recompute is ~10 ms and **all of it** was that forced layout (`changed=0`, empty document); the content-settle recompute of a 1589-line pom is ~25 ms — detect ~15, blockComments+markers ~8, graphics ~2 — so the scans themselves are *not* where the time went. **Ruled out with evidence, don't re-attempt blind:** the ~60 ms in `ConfigMigrations.readVersioned` is Jackson **warm-up**, not I/O or parse volume — every config file is ≤5.5 KB, so lazy-loading fewer of them saves almost nothing; and **deferring a background tab's fold recompute** (~25 ms) is *not* safe as it stands — `restoreFolds` runs synchronously right after `loadInto` and `applyCollapsedStartLines` needs the regions, so a saved collapsed region would silently fail to re-fold. **A `--fast` CLI flag was measured rather than assumed and rejected:** its two halves are ~100 ms for turning **twelve** features off (LSP, debug, git, GitHub, plugins, TODO, spell, notes, local history, MCP, HTTP, update check — all already per-feature settings) and ~106 ms for skipping the session, which **`--no-session` already does** (and the `.deb` Expert entry already passes). Neither half can reach the ~80% of startup that is pre-`main` JVM+AOT, Jackson warm-up, FXML, and the load→paint itself. **Pre-`main` decomposed (Linux app image, JVM absolute timestamps correlated against a shell-stamped `EDITORA_PERF_T0`): ~220 ms is the jpackage native launcher *before the VM exists*, ~50 ms is VM init + loading ~12k classes, and the rest is the **JavaFX toolkit being started before `main`**.** The launcher's 220 ms is identical with the AOT cache on or off and with or without a display (a bare `java -version` is 18 ms *total*), so it is packaging overhead with no Java-side lever — and three intuitive suspects were ruled out with evidence, don't re-attempt them: **AOT mapping is free** (`-Xlog:aot` maps at 8 ms uptime, done by 20 ms — and turning it off makes even `--version` *slower*), **dynamic linking is free** (`LD_DEBUG=statistics`: ~82k cycles), and **no GPU pipeline is created** for `--version` (`prism.verbose` prints nothing). The toolkit half *does* have a lever and it is why **`com.editora.Launcher` is the module main class for every path**, not just the fat jar: with an `Application` subclass as the main class the FX launcher starts the toolkit first, so `main` began at ~435 ms with `fx-start` 6 ms later — nothing left to overlap. Entering through `Launcher` moves `main` to ~297 ms with `fx-start` **142 ms** later, and `App.main` spends that window loading the config on a `config-prefetch` daemon thread (`prefetchConfig`/`takeBootstrap`); `config-loaded` drops 86 → 40 ms and first paint **1017 → 971 ms (−46 ms, interleaved, 11 pairs)**. The residue is `Fonts.load` (~40 ms), which needs the toolkit and so cannot move. `takeBootstrap` falls back to an inline load when the prefetch failed or the config dir disagrees, so the prefetch can only make startup faster, never add a failure mode. **Keep `Launcher` as the declared main class in all three pom sites** (`javafx-maven-plugin` `mainClass`, the jpackage `module`, the `moduleMain` argument passed to `scripts/aot_build.java`) — pointing any back at `App` silently closes the window again with no test failing. **Two things measured here that were *not* worth doing, so they aren't:** deferring the console tool-window panels out of `FXMLLoader.load()` (the FXML phase drops 125 → 105 ms and the saving reappears in `controller-init`/`window-shown` — the class loading is shared with the editor, so whichever surface touches it first pays, and deferring three of four consoles merely elected the fourth), and deferring the pre-paint spell/config-write/watcher work (~7 ms/run, not the ~120 ms it looks like — **the sampler prints sums over all runs; divide before believing a line item**). **And run a startup A/B *interleaved*, alternating the two builds run-by-run** — a sequential before/after across two dist builds reported this very work as a ~60 ms **regression** that 12 interleaved pairs showed was drift.
- **Code style — Palantir Java Format, enforced by Spotless.** All Java is auto-formatted with [Palantir Java Format](https://github.com/palantir/palantir-java-format) (a lambda-friendly, 120-col fork of google-java-format) via the `spotless-maven-plugin` (config in `pom.xml`; versions in the `${spotless.version}`/`${palantir.version}` properties). **Run `mvn spotless:apply` before committing** — `mvn spotless:check` is bound to the `verify` phase, so `mvn verify`/`mvn package`/CI fail on unformatted code (the `mvn javafx:run`/`mvn compile` dev loop is deliberately left untouched). Pipeline: `removeUnusedImports` → `palantirJavaFormat` → `importOrder` → `toggleOffOn`. **Import groups** (blank-line separated; longest-prefix wins, so `javafx` is *not* swallowed by `java`): JDK (`java`/`javax`) → `javafx` → everything else (third-party + `com.editora`) → static imports last. Escape hatch for hand-aligned code: wrap it in `// spotless:off` … `// spotless:on`. Palantir 2.72.0+ supports JDK 25. The two tree-wide mechanical reformats are recorded in `.git-blame-ignore-revs` (enable locally once with `git config blame.ignoreRevsFile .git-blame-ignore-revs`; GitHub honors it automatically) so `git blame` skips them.
- **Code size — soft limits, not hard gates.** Keep classes and methods small enough to hold in your head; these are review heuristics, not a build check. **Per class (target):** ≤ ~500 lines is ideal, ≤ ~1000 is fine; **~1000–1500** is acceptable only for a *genuinely cohesive subsystem* (e.g. `editor/EditorBuffer`, which coordinates one buffer's many overlays/managers — treat it gently); **> ~2000 lines is a refactor smell** — split it. **Per method (target):** ≤ ~50 lines ideal, **> ~100 is a smell** (extract helpers / a pure decision function). What actually matters is **responsibility count** and **cyclomatic complexity**, not raw line count — a 600-line class doing one thing is healthier than a 300-line class doing five. When a class creeps over the line, the first move is to extract the *pure* logic (a decision/format/parse helper in its own class, unit-tested) and, for a whole feature, a **`CoordinatorHost`-style coordinator** (see the `ui/*Coordinator` classes). **`ui/MainController` is the known outlier** (~12k lines) and is being incrementally decomposed one feature at a time into `ui/*Coordinator` classes (External Tools, Macros, TODO, Search, Run done; Notes, Bookmarks, LSP, Debug pending) — so **a new feature should be its own coordinator (or pure package), never bolted onto `MainController`**. No tooling enforces these numbers (JaCoCo gates *coverage*, not size); they're for human judgement during review and when deciding where new code lives.
- **Palette gating lives in `ui/Chrome`, and has two independent dimensions.** A command the palette can't run is **listed but grayed out and inert** (skipped by the selection cursor, ignored by Enter/click) rather than hidden, so the user still sees it exists and what its keybinding is (#532). `Chrome.paletteEnabled(id, gates, context)` ANDs the two halves, both pure + unit-tested in `ChromeTest`: **(a) `PaletteGates`** — the feature is switched off; driven by the `FEATURE_RULES` table (an `enabled` predicate + an id prefix + any exact `tool.*` ids), so **adding a feature is one record component + one table row**, not another `if`. **(b) `PaletteContext`** — the feature is on but there is nothing to act on right now (no buffer, wrong file type, no repo, no suspended debug session); these commands would no-op with a status message if run. `MainController.paletteGates()`/`paletteContext()` snapshot the live state, and the palette takes that snapshot **once per refresh, not once per command** (`CommandPalette`'s ctor takes a `Supplier<Predicate<Command>>`) — the predicate runs over the whole ~550-command registry on every keystroke in the query field, and the context half reads the active buffer, whose `hasPreview()` sniffs buffer text. Two invariants: a feature's **master enable toggle must not match its own gate** (they live under the never-gated `view.`/`appearance.` prefixes, or turning a feature off would gray out the command that turns it back on — `ChromeTest.masterEnableTogglesAreNeverGated` guards this), and the context rules stay **conservative** — graying a command that would in fact have worked is a worse regression than leaving one lit, so only families where *every* member needs the same context are listed (`git.clone` is the explicit carve-out from the in-a-repo rule). `PaletteContextFxTest` guards the wiring end-to-end in both directions. **A grayed row explains itself on hover**: `Chrome.disabledReason(id, gates, context)` returns a `DisabledReason{messageKey, commandArg}` — i18n **keys**, not text, so `Chrome` stays catalog-free — which `MainController.disabledCommandReason` resolves, filling `{0}` with the *localized title* of the command that would re-enable the feature (so the tooltip names something the user can type into that same palette). `paletteVisible`/`contextEnabled` are **derived from** `featureReason`/`contextReason`, so a command can never be grayed for a reason the tooltip can't state. Two subtleties: the feature reason **outranks** the context reason (telling someone to open a Markdown file when Markdown-lint is off sends them nowhere), and a feature that **Simple UI mode** forces off (`FeatureRule.simpleSuppressed`, declared via `simpleRule(...)` — git/github/lsp/http/localHistory/mcp/plugins/externalTools/log/testRunner/debug/ai/agent) points at `view.toggleSimpleMode` while Simple mode is on, since its own toggle would be a dead end.
- **Adding a feature = add a `Command`, and surface it in the command palette.** Every time we add a command or an applicable user-facing feature, it must be discoverable in the palette. Register it in `MainController.registerCommands()` and, if it needs a key, add a binding to `emacs.json`. The palette is populated from `CommandRegistry.all()`, so a properly registered command appears automatically — never add a user-facing action that bypasses the registry. Toolbar buttons and the palette both dispatch through commands; don't wire UI handlers to logic directly when a command fits.
- **Every setting also needs a palette command** — Editora is command-driven, so a Settings-window control (toggle, picker, font, path, number, …) is **not** enough on its own; it must have a command-palette equivalent too. Register a command in `MainController.registerCommands()` that flips/prompts the **same** `Settings` field, persists (`requestSave()`), re-applies the feature (`applyGitSupport`/`applyLspSupport`/`applyViewSettingsToAllBuffers`/…), and keeps an open Settings window in step via `SettingsWindow.syncAll()`. Toggles → `view.toggle*` (master feature-enable toggles use a `view.`/`appearance.`/`debug.` prefix so the palette's feature-gating filter never hides them); values → a `promptText` prompt or a `QuickOpen` picker; many per-item settings (e.g. the per-server LSP / per-adapter Debug commands) → one grouped picker command. Reuse the generic helpers `toggleSetting`/`promptStringSetting`/`promptIntSetting`/`chooseSetting`, and add `command.<id>` + `command.<id>.desc` to all six i18n catalogs (the two shared status keys `status.settingToggled`/`status.settingChanged` reuse the command's own title). The 2026-06 sweep (PR #56) closed every gap — keep parity when adding a setting.
- **Every user-facing string is localized — never hardcode UI text.** Any new label, status/echo message, tooltip, dialog title/header/body, button, menu item, prompt, or placeholder must go through the i18n catalog: `import static com.editora.i18n.Messages.tr;` then `tr("some.key")` (or `tr("key", args…)` for `MessageFormat` parameters like `Saved {0}`) — never pass a raw English literal to a JavaFX control. **Add the key to all six `resources/com/editora/i18n/messages[_<lang>].properties` files** (English base + `it/es/fr/pt/de`) with a real translation in each; `MessagesTest`'s key-parity check fails the build if any locale is missing a key. New `Command`s get their title for free via `Command.of(id, runnable)` + a `command.<id>` key. Only deliberate exceptions stay literal: technical tokens (`UTF-8`, `LF`/`CRLF`, `Ln`/`Col`, git verbs in `gitlabel.*`, detected language names, example URLs) and the pre-GUI `--help`/`--version` text. See the `i18n/` architecture bullet for the full system.

Window-icon PNGs (16–512) live in `resources/com/editora/icons/` (loaded into `stage.getIcons()` in `App`; also the About-dialog logo). - **Context-menu icons:** **every right-click `MenuItem` carries a leading icon** (`MenuItem.setGraphic(...)`). UI-package menus (tab strip + Welcome close in `MainController.installTabMenu`, `ProjectPanel`, `GitPanel`, `BookmarksPanel`, `NotesPanel`, `MessageLogPopup`, `FileBreadcrumb`) use `com.editora.ui.Icons` directly; the **editor** package's menus (`EditorBuffer.installContextMenu` + `showPreviewContextMenu`) can't depend on `ui`, so they use **`com.editora.editor.MenuIcons`** — a package-local mirror of `Icons` (same Material 24dp single-path glyphs, `toolbar-icon` style class, 0.8 scale) holding only the glyphs those two menus need (cut/copy/paste/undo/redo/selectAll, markdown bold/italic/strike/code/link, LSP goto-def/refs/hover, spellcheck/add/block, note/run/download/print); the Run item reuses `FoldManager.runGlyph()`. The recent-files toolbar **MenuButton** dropdown is not a right-click menu and is intentionally excluded (its entries already carry an inline remove-icon); the snippet **choice** dropdown lists content values, not commands, and is likewise excluded.
- **File-type icons:** **`com.editora.ui.FileIcons`** maps a file name to a small monochrome glyph reflecting its type, shown wherever a file is listed: editor tabs (`MainController.updateTabMeta`), the `ProjectPanel` tree (file rows; folders keep `Icons.project()`), the `FileFinder` file/folder pickers, the `Switcher` cell, and the **Open Files** / **Recent Files** `QuickOpen` pickers (via the new optional `QuickOpen.setItemIcon(Function<T,Node>)`). The pure, unit-tested **`FileIcons.iconKeyFor(name)`** resolves a name → glyph key — non-language extensions first (image png/jpg/svg/…→`image`, `pdf`, archive zip/jar/…→`archive`, csv/tsv→`table`, `*.lock`, txt/log→`text`), else `LanguageRegistry.forFileName(name)`'s language id → key (java/python/js/ts/go/php/ruby/c/cpp/csharp/kotlin/html/css/markdown/yaml/json/xml→code/shell/powershell+batchfile→terminal/dockerfile/terraform/mermaid/sql→storage/ini+toml+…→settings/rust+lua+groovy+http→code); unknown ⇒ `generic` → the existing `Icons.fileSheet()` fallback (so unrecognized files look exactly as before). **`forFileName(name)`** turns the key into a fresh `Icons.of(path)` node — glyphs are single-path SVGs in the `toolbar-icon` style (theme-aware, no per-theme overrides, **no new CSS**). Brand logos are vendored from **Simple Icons** (CC0); category glyphs from **Material Design Icons** (Apache-2.0) — attributed in `NOTICE`. `Icons.of(...)` was made package-private so `FileIcons` (same package) reuses it. To add/adjust a mapping: extend the `iconKeyFor` switch + add the glyph path to `FileIcons.PATHS` + a `FileIconsTest` case. *(No new dependency; glyphs are inlined path strings, like the existing browser logos.)*
- **Bundled fonts:** five monospace families ship under `resources/com/editora/fonts/<family>/` (Regular/Bold/Italic/BoldItalic TTFs; Fira Code has no italic), **plus Inter** (sans-serif, `fonts/inter/`) as the Markdown **preview + PDF prose** font. `Fonts.load()` registers them all via `Font.loadFont` at the very start of `App.start` (before any CSS), so they resolve by family name regardless of the OS. `Fonts.BUNDLED` (JetBrains Mono first = default) is the **monospace** editor-font picker list and deliberately **excludes Inter** (Inter isn't an editor font); it's listed ahead of the system monospaced families in the Settings font picker. Inter is the preview prose font on **all platforms** (`.markdown-preview .md-text` in `app.css` — pinned explicitly because raw `Text` nodes don't reliably inherit the scene font, and because the macOS chrome's logical "System" family can't be bold-rasterized cleanly by JavaFX) and the PDF prose font (`MarkdownPdfWriter`). They're plain resources (no `module-info`/moditect change) and are picked up by the `dist` build automatically. Attributed in `NOTICE` (all OFL-1.1).
- **"Caret & Ink" — the flagship theme + the state language (UI Kit v1).** `Editora Light`/`Editora Dark` are the **first-run default** (`Themes.DEFAULT`/`EditorThemes.DEFAULT`/the `Settings.theme`+`editorTheme` field defaults). Because Jackson persists every modeled field, **an existing install keeps whatever `settings.toml` already holds** — only a fresh config dir picks the default up. The palette derives from `branding/editora-icon.svg`: Caret teal accent (`#0e8577` light / `#43dec5` dark), Ink navy `#1b1e2a` (light-mode text *and* dark-mode surface), Porcelain `#f4f5f9` / Abyss `#12141d` grounds, and **Brace periwinkle reserved exclusively for the keyboard**. The control stylesheets `styles/atlantafx-themes/editora-{light,dark}.css` are **authored, not vendored**: their `.root` palette block is hand-written and the ~4855-line component body is the vendored Blue theme's (a light/dark pair's bodies differ only in ~40 `base-1`↔`base-6/7` hover/selected swaps, and the body references just `base-1/2`, `accent-6`, `success-5`, `danger-6`). A token the body references but the palette omits **fails no build** — JavaFX leaves the property unresolved and the control silently renders a default color — so `ThemesTest.flagshipPaletteDefinesEveryTokenTheVendoredThemesDo` pins the token set against `blue-light.css`. Unlike the community themes the pair does **not** use `adaptive.css`: the kit pins its syntax palette to the Primer token colors, which the adaptive mapping (keyword→`danger`, string→`success`, number→`accent`) cannot express, so it ships `styles/editor-themes/editora-{light,dark}.css`. **`EditorThemes.BARE`** (= `Primer Light`) is now the one theme with no override stylesheet — that used to be `DEFAULT`, and anything keying "has no override" off `DEFAULT` breaks the moment the default moves. **State language** (`app.css`): each meaning is named once as a looked-up color on `.root` — `-state-amber` "not durable yet" (unsaved/read-only/narrowed/snapshot), `-state-red` broken, `-state-green` verified, `-state-accent` the app is offering something, `-state-olive` untracked, `-state-violet` renamed, `-state-key` **the keyboard and nothing else** — and every surface (tabs, status pills, trees, pickers, Settings) references those instead of restating a hex. The first four chain to the theme's semantic roles so they track it for free; **periwinkle has no AtlantaFX role**, so `app.css` carries a both-grounds compromise (`#7078c0`) that the flagship editor themes override with the kit's exact light/dark pair. Replacing the old hardcoded `#bf8700` dirty-amber with `-state-amber` means dirty markers now **track the theme** rather than staying one fixed ochre.
- **UI chrome font — Inter, all platforms** (`styles/ui-font.css`, attached per-scene by `App.installUiFont`). Not inherited from anywhere: **AtlantaFX 2.1.0 neither bundles nor references Inter**, and no bundled theme sets a `.root` `-fx-font-family`, so without this sheet the whole interface falls back to JavaFX's default logical "System" — which is why the app looked unlike the kit's mockups even after the palette landed. It is a *scene* stylesheet (not an `app.css` rule) because dialogs and popups each live in their own scene, and because a scene sheet survives a runtime `setUserAgentStylesheet` theme switch. `Fonts.load()` must register Inter **before** any stylesheet is applied or the family won't resolve. This **replaced** the macOS-only `ui-system-font.css` San Francisco experiment: it made the UI differ by OS for no design reason, and JavaFX can't rasterize `.AppleSystemUIFont`'s bold cleanly (it faux-bolds and mangles glyphs — the same reason the Markdown preview was already pinned to Inter). `.editor-area` sets its own `-fx-font-family`, so the editor surface is untouched.
- **Icons are two families, mid-migration** (`ui/Icons`). **`Icons.line(d)`** renders the UI Kit's 16-unit **outline** glyphs — stroked, `icon-line` class, coloured by **`-fx-stroke`**; **`Icons.of(d)`** renders the older Material 24dp **filled** single-path glyphs — `toolbar-icon` class, coloured by **`-fx-fill`**. **The default toolbar is now entirely `line`**: `open`, `openFolder` and `saveAs` were still filled Material glyphs, and the Open folder in particular was the one solid shape in a row of outlines. `open` carries the open-folder silhouette and `openFolder` the closed one — deliberately the same closed folder as `project()`, since both mean the project, so matching there is coherent while the *different* action gets the different shape. `template()` is new: New-From-Template borrowed `fileSheet()`, whose path is `newFile()`'s minus the little plus, so the two adjacent "new file" buttons differed by one cross; it is now a page with content lines. A default toolbar widget takes its glyph from `setupButton`, **not** from the catalog's `iconKey` (which only builds the *extra* buttons), so changing one means changing both. The kit specifies 34 glyphs (the toolbar / tool stripe / tab chrome its mockups draw); Editora has ~160 across `Icons`/`MenuIcons`/`FileIcons`, so 33 are converted and the rest stay Material until a full line set is authored. **The two families are not interchangeable**: a line glyph must NOT also carry `toolbar-icon`, because any `X .toolbar-icon { -fx-fill: … }` rule outranks a bare `.icon-line` and would paint the outline solid — so each context a line glyph appears in carries its own `-fx-stroke` rule in `app.css`. The kit authors its glyphs as `<symbol>`s mixing `<path>`/`<circle>`/`<rect>`, and `SVGPath` takes only path data, so circles and rounded rects are converted to **arc commands** — precisely the construct JavaFX's parser silently fails on (see the Cargo/Go/Gradle blank-icon note), hence `IconsFxTest.everyKitLineGlyphRendersANonEmptyShape` asserts every converted glyph has non-empty bounds.
- **Theming:** AtlantaFX is the user-agent stylesheet and themes standard controls (`Themes`, set via `Application.setUserAgentStylesheet`). It does **not** style the RichTextFX `CodeArea` — editor surface, line-number gutter, and syntax token colors live in `styles/app.css` + `styles/syntax.css` (the **Primer Light** defaults). **Editor color themes** (`EditorThemes`) layer an override stylesheet from `styles/editor-themes/<name>.css` onto the scene *after* those defaults (Primer Light = no override); `MainController.applyEditorTheme` swaps that sheet on the scene and sets each buffer's current-line highlight color (RichTextFX's line-highlight fill is set in code, not CSS). The editor theme follows the AtlantaFX theme (`EditorThemes.defaultFor`) until the user picks one (`Settings.editorThemeUserSet`). Token rules must stay the compound `.text.<class>` form — see the header comment in `syntax.css`. The **Project tool window file tree** is themed via two looked-up CSS colors `-project-folder-color`/`-project-file-color` (defined on `.project-tree` in `app.css`, defaulting to AtlantaFX accent/muted); each editor theme overrides them, so a new editor theme should add a `.project-tree { -project-folder-color: …; -project-file-color: …; }` rule. **Bundled community themes:** beyond the 7 built-in AtlantaFX themes (Primer/Nord/Cupertino/Dracula), `Themes` also lists 19 MIT-licensed community themes from the DLSC `atlantafx-themes` collection (Blue/Navy/Army L/D, the four seasonal L/D sets, Autumn/Browny/News/Yacht — the GitHub colorblind/tritanopia variants are excluded on purpose). Their control-theme CSS is **vendored** under `styles/atlantafx-themes/<name>.css` (self-contained AtlantaFX user-agent stylesheets; `url()`s resolve to JDK modena assets) and served by `Themes.BundledTheme` — a small `atlantafx.base.theme.Theme` impl **kept in `com.editora.ui`** so `theme.getClass().getResource(...)` finds the vendored CSS in *this* module (a `Theme.of(...)` instance would resolve against atlantafx-base and return null). `Themes.BUNDLED` (name → {css base, dark, bg-default hex}) drives `themeFor`/`backgroundFor`. **The matching editor themes all share one file** — `styles/editor-themes/adaptive.css` — whose `.editor-area`/`.text.<class>`/`.project-tree` rules are written entirely in the theme's own `-color-*` semantic variables (keyword→`danger-fg`, string→`success-fg`, number→`accent-fg`, type→`warning-fg`, function→`accent-emphasis`, comment→`fg-muted`, …), so one palette adapts to every theme with no per-theme syntax file. `EditorThemes` still needs per-theme **code-driven** colors that CSS vars can't reach (startup background, current-line highlight, minimap block/viewport), taken from each theme's `-color-bg-default`/`-color-fg-default`/`-color-bg-subtle`/`-color-fg-muted`/`-color-accent-emphasis`. **To add another AtlantaFX theme:** vendor its `.css`, add a `Themes.BUNDLED` entry + the name to both `Themes.NAMES`/`EditorThemes.NAMES`, and add `EditorThemes` map entries (CSS→`adaptive`, plus the 5 code-driven colors). `ThemesTest` guards that every theme resolves a loadable stylesheet + has a matching editor theme + parseable colors. Community-theme CSS is MIT (attributed in `NOTICE`). **User-defined themes** (`ui/UserThemes`, loaded once in `App.start` via `UserThemes.load(configDir)` before the theme is applied; palette command `theme.reloadUserThemes` re-scans): two folders under the config dir — **`themes/*.css`** = full AtlantaFX control themes (each becomes an app theme *and* an adaptive editor theme, exactly like the bundled community ones — served via a file-URL `BundledTheme` + `adaptive.css`, with code-driven colors parsed from the CSS's `-color-*`), and **`editor-themes/*.css`** = hand-authored editor overrides (editor-theme picker only, served by the file URL). **A user theme file must declare at least one `-color-*`/`-fx-*`** (`looksLikeStylesheet`) — every `.css` in the folder is offered, so an empty/half-written one otherwise became a pickable theme that strips AtlantaFX from the app — and **`parseColor` follows a token defined by reference** (`-color-bg-default: -color-dark-1;`, bounded to `MAX_VAR_HOPS`, cycle-safe) and won't match a longer token that merely starts with it: the bundled themes and upstream AtlantaFX all use literal hex, so a reference-style theme silently parsed as *no colour* → white bg + `dark=false` → dark chrome around a white editor. The picker/combo lists now come from `Themes.names()` / `EditorThemes.names()` (built-ins + user), not the static `NAMES` (kept as the built-in list); `normalize`/`defaultFor`/`stylesheetFor`/the color accessors consult `UserThemes.controlThemes()`/`editorThemes()`. The theme **name is the file base name Title-Cased** (`my-theme.css` → "My Theme"); a name colliding with a built-in is skipped. `UserThemes.titleCase`/`parseColor`/`baseName` are pure/unit-tested; a user theme's `file:` URL passes straight through `Themes.stylesheetFor`'s `hasUrlScheme` check.
- **Tests** are mostly **pure logic** (keymap resolution, command registry, config merge, highlighting spans), plus a small **headless-JavaFX harness** for toolkit-bound `ui/` behavior (see below). A third tier exists for code that talks to an **external process**: rather than fork one, inject a recording test double through a `*ForTest` seam — `LanguageServerSession.attachForTest(LanguageServer, ServerCapabilities)` and `LspManager.setSessionStarterForTest(Consumer<LanguageServerSession>)`, both inert in production, with `FakeLanguageServer` capturing the params. **This tier exists because its absence was measured, not guessed:** an audit found four defects in `com.editora.lsp` (#715/#723/#724/#725), and `LanguageServerSession` was then at **3.2%** line coverage with `LspManager` at **17%**, while the pure mappers beside them (91-100%) had produced none — the two were unreachable without a subprocess, so **nothing asserted what Editora puts on the wire**, which is exactly what #725 (an unreachable `TriggerCharacter` branch) and #715 (an off-by-one range) were. When adding a request, assert its *params*, not just that the call compiles; `ClientCapabilitiesTest` likewise pins what we **declare** at `initialize`, since a dropped capability fails no build and no test — the feature just quietly stops working on one server (#468, #674, #676 all died that way). Prefer extracting pure decision helpers and unit-testing those (it's faster + needs no toolkit) — but real controller behavior (Zen toggling chrome, Simple-mode stripping, tab/window lifecycle) is now covered end-to-end via the FX harness. **Coverage:** `mvn test` runs the JaCoCo agent and writes a report to `target/site/jacoco/index.html` (+ `jacoco.xml`); `mvn verify` additionally runs a JaCoCo **`check`** that enforces a per-package LINE-coverage **floor** on the well-covered pure packages (migration·diff ≥0.90, config ≥0.86, template·editorconfig ≥0.82, completion·http·pdf ≥0.70 — see the `jacoco-check` execution in `pom.xml`), so their coverage can't silently regress. Floors sit comfortably below current levels (a regression net, not a target) — **when you raise a package's coverage, ratchet its floor up**. `ui`/`editor` are still **deliberately ungated** (the FX harness covers only a few % of `ui`'s ~16.7k lines so far — add a floor only once coverage is meaningful). The dev loop (`mvn javafx:run`/`compile`) is unaffected — the check runs only at `verify`/`package`. The cheapest way to raise `ui` coverage is still to extract pure decision helpers (effective-visibility/gating predicates, caret-navigation math, path keying, …) and unit-test those — see `ui/Chrome`, `editor/TextNav`, `config/PathKeys`.
  - **Sample corpus (`samples/`)** — a curated, feature-organized set of small text samples for **manual** smoke-testing/demos (one subdir per feature: `syntax/` per language, `folding/`, `indent/`, `markdown/`, `mermaid/`, `todo/`, `spell/`, `search/`, `editorconfig/` (hermetic, `root=true`), `http/`, `log/`, `diff/`, `encodings/`). It's a **human aid**, not part of the behavioral suite; `samples/README.md` is the manifest and `SamplesCorpusTest` only guards that the manifest ↔ committed files stay in sync + the core languages each have a syntax sample (add/remove a sample ⇒ update the README or the test fails). Large/perf inputs are **generated** by `java scripts/GenSamples.java` (a JDK 25 compact source file, run from the repo root) into the git-ignored `samples/perf/` (never committed — keeps history lean). A scoped root `.gitattributes` marks `samples/encodings/**` + `samples/diff/conflict.txt` `-text` so git never normalizes the encoding/EOL/conflict-marker bytes, and `samples/**` `linguist-vendored`. Samples are inert-by-name (no real `.gitignore`/secrets; the EditorConfig fixture is sandboxed with `root=true`). Spotless only formats `src/{main,test}/java`, so sample `.java` files are left untouched.
  - **Headless-FX harness** (`src/test/java/com/editora/ui/`): **TestFX** (`testfx-core`/`testfx-junit5`) drives only the toolkit **lifecycle** (`FxToolkit.registerPrimaryStage()`) over **JavaFX 26's built-in Headless Glass platform** (`-Dglass.platform=Headless`, part of `javafx.graphics` since 26 — no Monocle jar, no native libs) — so FX tests run headless on CI with **no display/xvfb**. The harness never drives the TestFX **robot** (no `clickOn`/key simulation — everything goes through `runOnFx`/`callOnFx` + reflection), so the prototype headless platform's input/rendering limitations don't apply, and TestFX needs no changes despite not yet officially adopting the new platform. All FX tests are `@Tag("fx")`; run the pure suite alone with `./mvnw test -DexcludedGroups=fx`. `FxTestSupport` boots the toolkit once (Headless platform + `Fonts.load`/`Messages.init`/AtlantaFX UA sheet/classloader pin) and exposes `runOnFx`/`callOnFx` + reflection helpers (`field`/`invoke`/`call`) to read private `@FXML` nodes and invoke private methods (tests run on the **classpath** as the unnamed module, so `setAccessible` is unrestricted). `FxWindowFixture` builds a real window via `WindowManager.buildWindowForTest()` (a package-private seam mirroring `buildWindow`) against a temp config dir — **if that boot path changes, the fixture/seam must track it**. The **surefire config** is what makes this work: `<useModulePath>false</useModulePath>` (classpath mode), the headless system properties (`glass.platform=Headless`, `prism.order=sw`), and **`<argLine>@{argLine}</argLine>`** — the `@{argLine}` token is mandatory so JaCoCo's injected coverage agent (set via the `argLine` property) survives; a plain `<argLine>` would clobber it.
